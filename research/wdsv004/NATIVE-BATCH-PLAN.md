# Native batch preparation

batch_plan.c/h resolve the complete current snapshot and build the next private manifest without performing I/O. Changed records target slots opposite the selected references; unchanged reference rows remain intact. The generation exceeds every structurally valid observed manifest, including incomplete newer candidates. Empty batches, absent baselines, conflicting generations, sequence/generation overflow, invalid records and replacements beyond the existing native capacity are rejected. Failures preserve output bytes.

The replacement API takes three encoded immutable buffers; NULL with zero size means unchanged, not deletion. Deletion is an encoded tombstone. The returned plan includes manifest bytes, target manifest slot, changed-member mask and target record slots. The caller retains ownership of all record bytes and must hold exclusive ownership until publication or recovery. No writer, file adapter, migration or initialization is implemented here.

Thirteen ARM/Thumb cases pass against batch_plan.py, comparing all 208 output bytes on success and unchanged output on failure. These cover unchanged references, two-member updates, empty live data, tombstones/new members, missing baselines, empty batches, invalid sequence/truncation/oversize, the exact 163840-byte payload limit, generation and sequence exhaustion, incomplete higher-generation candidates and conflicting baselines. The linked recovery and SHA implementations execute natively under emulation; no digest hooks are installed. The standalone build has no undefined symbols. Results and original test ELF hash are in batch-plan-arm-results.json; the ELF is not published.

The planner currently computes the replacement digest twice, once to form a reference and again during full record validation. This favors reuse of validation over performance; no Vita performance claim is made. The next step is a native publication coordinator that writes and reads back records before publishing the manifest, blocks after uncertainty and requires recovery before reuse. Readback alone will not prove durability. INI-DATA of 512000 bytes remains unsupported by the native writer limit. No client or physical console execution occurred.
